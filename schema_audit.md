# Schema Introspection Audit — how thoroughly each backend captures schema

Scope: `server/backends/{base,postgres,mysql,mssql,oracle,redshift,snowflake,databricks,bigquery,mongodb_sql,sheets}.py`, cross-checked against `server/translate_routes.py` and `server/db.py`. Every finding below is grounded in the actual `get_schema()` code, not assumption — file/line references are given so anything here can be re-verified directly.

## The baseline the question is measured against

`Backend.get_schema()`'s own abstract docstring (`base.py`) names the target checklist explicitly: *"tables, constraints, indexes, views, grants, triggers, or the closest per-backend equivalents."* Postgres — the original, single-dialect implementation — hits essentially all of it: tables/columns (with type, nullability, default), constraints (PK/FK/unique, via `information_schema.table_constraints`), indexes (`pg_indexes`), views, grants (`information_schema.role_table_grants`), and triggers. Every dialect added afterward was benchmarked against that same six-item list in its own module docstring, and every one of them consciously dropped at least one or two items, with the drop explained inline. Nothing added later comes close to matching Postgres's coverage, and none of them ever claim to.

Two things the Postgres baseline itself never covered, in any version: stored procedures/functions, and sequences. Neither appears in any of the 10 backends. Materialized views, table/column comments, and partitioning metadata are also absent everywhere except two narrow exceptions noted below (Oracle excludes materialized-view storage tables from its table list but doesn't describe the materialized views themselves; Redshift substitutes a distribution/sort-key section for what would be partitioning-adjacent context). So "thorough, Postgres-original" itself was never "every SQL concept" — it was tables/columns/constraints/indexes/views/grants/triggers, and that's the fair yardstick.

## What every non-Postgres/MySQL backend gave up, and why

Indexes disappear for five of the eight SQL backends (MSSQL, Oracle, Redshift, Snowflake, Databricks), for two different reasons that get conflated in the matrix above but are worth separating:

Redshift, Snowflake, Databricks, and BigQuery have **no user-facing index concept at all** — omitting the section isn't a gap, it's correctly reflecting reality (Redshift substitutes DISTKEY/SORTKEY instead, which is arguably a better fit for what actually matters to those engines' query planning). MSSQL and Oracle, by contrast, **do** have real, queryable index catalogs (`sys.indexes`, an equivalent to `pg_indexes`) — their own module docstrings say so explicitly and call the omission a deferred first-pass gap, not a "doesn't apply" case. That is a real, closeable gap, not a design constraint.

Triggers disappear for six of eight (everyone but Postgres/MySQL). Redshift and Snowflake/Databricks/BigQuery genuinely have no trigger support to query. MSSQL and Oracle do support triggers and defer them the same way they defer indexes.

Grants disappear for seven of eight (everyone but Postgres/MySQL). This is the most uniform gap: every other dialect's docstring describes its own grants story as either genuinely inconsistent across versions (Redshift), unverified against a real account/workspace (Snowflake, Databricks), or simply not attempted (MSSQL, Oracle, BigQuery). None of them claim "this dialect has no such concept" the way indexes/triggers legitimately can for some engines — a real, closeable gap across the board.

Constraint enforcement semantics are inconsistent in how clearly they're surfaced. Redshift and MSSQL both put an explicit sentence in the schema text itself telling Gemini whether PK/FK/UNIQUE are enforced ("declared only" vs. "enforced at write time"). Snowflake, Databricks, BigQuery, and Oracle don't — a query built assuming referential integrity holds could silently be wrong for exactly the same reason on any of those four, but the model is never told so via the schema text on those four the way it is for Redshift/MSSQL. This is a copy-paste inconsistency between otherwise-parallel modules, not a deliberate per-dialect decision — nothing in Snowflake's/Databricks'/BigQuery's own docstrings argues against adding the same sentence.

Two structural items are missing everywhere, including Postgres, and always have been: stored procedures/functions and sequences. Oracle's `execute()` has real, substantial PL/SQL-block-execution support (DBMS_OUTPUT capture, the `/`-terminator convention, `_PLSQL_UNIT_RE`) — the app can clearly *run* a stored procedure a user writes inline — but `get_schema()` never enumerates a database's existing procedures/functions/packages so a user could ask "what does the `recalc_totals` procedure do" and have Gemini see it. This is the single largest asymmetry in the whole audit: heavy execution-side investment in one dialect's procedural-code support, with zero introspection-side visibility into what procedural code already exists there.

## Two items worth flagging as correctness findings, not just coverage gaps

**`dialect_name` is documented as unwired but is not.** `base.py` line 442-447's docstring for `Backend.dialect_name` says: *"Not wired into translate_routes.py yet - that prompt is still hardcoded to Postgres; parameterizing it by dialect_name is the next step after this refactor."* That's stale. `translate_routes.py` (lines 134-245, and used at lines 1664-1667 and 4290-4293) already keys a full `_DIALECT_PROMPT_INTROS` dict by `dialect_name`, with `get_backend(descriptor).dialect_name` selecting the right one and falling back to the Postgres intro only when a descriptor can't resolve a backend at all. Every one of the 10 dialects already gets its own tailored prompt intro (identifier-quoting rules, three-level namespace warnings for Databricks, the PL/SQL `/`-terminator instruction for Oracle, the read-only warning for MongoDB, the no-FROM-clause/letter-addressing rule for Sheets, etc.) — this part of the architecture is actually further along than its own comment claims. Worth a one-line fix to the comment so the next person reading `base.py` doesn't repeat the same stale belief.

**Databricks' `table_type` mismatch was a real, shipped bug, not a hypothetical.** `databricks.py`'s own comment (lines 170-181) says the ANSI `'BASE TABLE'` filter every other ANSI-ish dialect uses "silently matched zero rows against a real workspace (this was caught after shipping, against a real connection - the fake DB-API harness ... has no opinion on table_type values, so nothing here would have failed a test either way)." This is worth surfacing to you directly: it means the fake-harness test suite (`tests/server/helpers.py`) structurally cannot catch a wrong-enum-value class of bug for any dialect, since it never encodes real catalog-view value vocabularies. Oracle's/MSSQL's/Redshift's/Snowflake's own "NOTE for reviewers" paragraphs all say outright they've only been exercised against that same fake harness, never a real instance — so each of those five backends' `get_schema()` carries the same class of unverified risk Databricks' `table_type` value already actually manifested once. This isn't asking you to do anything right now — it's flagging that "exercised against the fake DB-API harness" and "verified" are not the same claim, and the one dialect that got a real test (Databricks) is also the one dialect that turned up a real bug.

## Shared infrastructure that applies uniformly (and doesn't vary per dialect)

A few caps exist for every SQL-style backend (Postgres/MySQL/MSSQL/Oracle/Redshift/Snowflake/Databricks/BigQuery), all defined once in `base.py` and simply reused, rather than reimplemented per dialect: `SCHEMA_MAX_TABLE_NAMES_SCANNED` (20,000 — bounds the cheap phase-1 name scan), `SCHEMA_MAX_TABLES` (200 — how many tables/table-families actually get described in detail, with an "N more not shown" note appended when exceeded), `SCHEMA_SHARD_MIN_GROUP_SIZE` (3 — the minimum same-prefix date-suffixed table count before they're collapsed into one described "family"), and `SCHEMA_MAX_CHARS` (100,000 — a final text-length backstop via `cap_schema_text()`, applied identically everywhere, including Sheets/MongoDB which skip the shard-family machinery entirely since a single-tab/single-collection model has nothing to shard). This part of the design is genuinely dialect-agnostic and consistently applied — nothing to flag here.

Two backends opt out of the date-shard-collapsing machinery entirely, correctly: MongoDB (no equivalent naming convention exists for collections) and Sheets (one tab is one "table," so there's nothing to collapse in the first place). That's a deliberate, documented decision in both modules, not an oversight.

## Bottom line

If "thorough" means matching what the original Postgres implementation captured — tables/columns, constraints, indexes, views, grants, triggers — only Postgres and MySQL are still at that bar today. Every other SQL dialect (MSSQL, Oracle, Redshift, Snowflake, Databricks, BigQuery) captures tables/columns/constraints/views solidly, but has zero grants coverage and is missing indexes and/or triggers either because the engine genuinely has no such concept (Redshift/Snowflake/Databricks/BigQuery for indexes and triggers both) or because that dialect's own first pass explicitly deferred a feature the engine does support (MSSQL and Oracle both defer indexes, triggers, and grants despite having real catalogs for all three). MongoDB and Sheets are structurally different enough (no writes, no real "database" in Sheets' case) that the checklist only partly applies to them, and both already capture everything meaningful their own model permits.

The most actionable gaps, in rough order of effort-to-value: (1) grants — closeable for MSSQL, Oracle, and BigQuery at least, since their catalogs support it and the only reason given is "not yet attempted"; (2) indexes for MSSQL and Oracle specifically, since both dialects were explicit that this is deferred, not unsupported; (3) a consistent "enforced vs. declared-only" sentence for Snowflake/Databricks/BigQuery/Oracle, matching what Redshift/MSSQL already say, since the underlying enforcement-or-not fact is just as true for those four and the model has no way to know it from the schema text alone today; (4) stored procedure/function enumeration for Oracle in particular, given how much execution-side investment already exists there with none of it visible at introspection time.





# What the schema block should contain — recommendations for best-possible query generation

Scope and framing: the prior audit (`schema_introspection_audit.md`) measured every backend against a fixed six-item checklist — tables/columns, constraints, indexes, views, grants, triggers — and found Postgres and MySQL alone hit it, with the rest deferring pieces their own catalogs actually support. This document asks a different question: not "does this backend match Postgres's original checklist" but "what would actually make Gemini write a correct query on the first try, against any of the ten backends, including ones whose catalogs were never designed with an LLM as the reader." The two documents complement each other — several items below close audit-flagged gaps, but most of what follows is metadata no backend captures today and the audit never asked about, because it lived outside the original checklist entirely.

Everything here is organized by what kind of query-writing mistake it prevents, since that's the actual test of whether it belongs in the prompt at all — not "is this a real database concept," which is a much lower bar. Feasibility is discussed per backend where it materially differs; where a recommendation is uniformly easy or uniformly hard across all ten, that's said once rather than ten times.

## Getting the shape of a value right, not just its type

The single highest-value gap across every backend today, including Postgres and MySQL, is that no backend surfaces actual data values anywhere except Sheets (which already samples up to three per column) and, incidentally, Mongo's ODBC-inferred types. A column named `status` typed `VARCHAR(20)` tells the model nothing about whether the real values are `'active'`/`'inactive'`, `'A'`/`'I'`, `'Active'`/`'Inactive'`, or `1`/`0` stored as text. This is almost certainly the largest single source of correct-looking-but-wrong queries in an NL-to-SQL system generally: the join logic and aggregation the model writes is usually fine, but a `WHERE status = 'Active'` predicate silently returns zero rows against a table that actually stores `'ACTIVE'`. No amount of structural metadata (keys, indexes, constraints) touches this failure mode at all.

The fix is to fetch the top N most frequent values for columns that look categorical — low cardinality relative to row count, typically text or short numeric/boolean-like columns — via a `GROUP BY ... ORDER BY COUNT(*) DESC LIMIT 15`-shaped query, or the backend's approximate-distinct-count equivalent where one exists (Snowflake's `APPROX_COUNT_DISTINCT`, Postgres's `pg_stats.n_distinct` as a cheap pre-filter before deciding whether a column is worth sampling at all). This has to be bounded carefully or it becomes the single most expensive part of schema introspection: a naive "sample every column of every table" pass multiplies introspection cost by the column count of the whole schema, and a free-text column with millions of distinct values makes the `GROUP BY` itself expensive for no benefit. The practical shape is a cardinality pre-check (distinct-count estimate, or just "under some row-count threshold, try it and cap the query with a time/row-scan budget") that decides per column whether sampling is worth attempting, then a hard cap on how many columns per table and tables per connection get this treatment at all — almost certainly not all 200 tables `SCHEMA_MAX_TABLES` already allows through, since sample-value text is one of the more character-expensive additions relative to a single column-type line.

Numeric and date columns benefit from a cheaper, different version of the same idea: min/max instead of a frequency table. Knowing an `order_date` column's actual range is 2019-03-01 through the present tells the model whether "orders from last year" is even a question this table can answer, and prevents it from writing a plausible-looking date filter against a column that's actually empty for the period asked about. This is a single `MIN()/MAX()` per column rather than a `GROUP BY`, so it's cheap enough to apply more liberally than full frequency sampling — every date/timestamp column, not just ones that clear a cardinality bar.

Feasibility differs by backend mainly in how expensive an ad hoc aggregate query is to run safely during schema introspection rather than in whether the SQL is expressible (every one of the ten SQL-capable backends can run a `GROUP BY`/`MIN`/`MAX` — this isn't a catalog-availability question the way indexes or grants are). BigQuery is the sharpest exception worth calling out by name: BigQuery bills by bytes scanned, and a `SELECT status, COUNT(*) FROM huge_table GROUP BY status` against an unpartitioned multi-terabyte table during routine schema-cache refresh could be a real, recurring cost surprise rather than a one-off. Any implementation should use `TABLESAMPLE SYSTEM` or query `INFORMATION_SCHEMA`-exposed statistics before falling back to a live aggregate, and should very likely skip live sampling entirely for tables above a configurable size threshold. Snowflake and Databricks (usage-based compute) share the same cost-awareness need, just less sharply than BigQuery's byte-scan billing model.

## Column semantics beyond the raw type name

`NUMERIC` without precision/scale, or `TIMESTAMP` without timezone-awareness, are both real but incomplete answers to "what does this column hold." `information_schema.COLUMNS` (or each backend's equivalent catalog) already carries `numeric_precision`/`numeric_scale`, `character_maximum_length`, and `datetime_precision`/timezone-awareness alongside the bare type name for every ANSI-ish backend here — this is metadata the existing queries are already close to, in most cases just not selecting the extra columns. Surfacing "TIMESTAMP WITH TIME ZONE" versus "TIMESTAMP WITHOUT TIME ZONE" specifically matters for generated date arithmetic and any query that compares a stored timestamp against `NOW()`/`CURRENT_TIMESTAMP`, since silently treating a naive timestamp as if it carried zone info (or vice versa) is exactly the kind of subtly-wrong-by-a-few-hours query that looks completely correct until someone checks the boundary rows.

Whether a column is auto-generated — `SERIAL`/`IDENTITY`/`AUTO_INCREMENT`, or a Postgres `GENERATED ALWAYS AS IDENTITY` — is worth one explicit marker per column rather than leaving it implicit in the default-value text. It matters for two different reasons: it tells the model never to suggest an explicit value for that column in an `INSERT`, and on backends where PK constraints are missing or unenforced (several are, per the audit), an identity/auto-increment column is often the strongest available signal for "this is the table's real surrogate key" even with no declared constraint to confirm it.

Collation is a smaller but real correctness factor, worth a single line rather than a whole section: whether string comparison on a given column or connection is case-sensitive changes whether `WHERE name = 'bob'` should be expected to match `'Bob'`. MSSQL in particular defaults to case-insensitive collations far more often than Postgres does, so a query that would be correct as written against one backend's default collation can behave differently against another's — worth surfacing once per connection (the effective default collation) rather than per column, unless a specific column overrides it.

## Relationships the catalog never declared

Five of the eight SQL backends here either don't enforce FK constraints at write time or don't reliably expose them — Redshift and MSSQL say so explicitly in their own schema text already; Snowflake, Databricks, Oracle, and BigQuery don't currently say so at all (an audit-flagged gap worth closing on its own). But a real, closeable gap sits underneath that one: plenty of production schemas encode relationships purely through naming convention — a `customer_id` column with no FK constraint pointing at `customers.id` — and today the schema text carries zero signal about that relationship on any backend where it isn't a real, declared constraint. A heuristic pass — a column whose name matches `<singular-or-plural-table-name>_id` (or `_key`/`_fk`, or just an exact name+compatible-type match against another table's primary key column) — can surface these as a distinctly-labeled "likely relationship, not enforced" line, separate from the real, constraint-backed foreign keys already in the "Constraints" section. This is deliberately a lower-confidence signal than a real FK and should read as one in the schema text (a different heading or an explicit "unconfirmed" qualifier), since a wrong guess here would suggest a join that doesn't actually hold — but zero signal is worse than a clearly-hedged one, especially for the backends whose real FK coverage is already the weakest.

View definitions deserve the same "prefer the real thing over metadata about the real thing" treatment. A view's SQL body is frequently the single best piece of business-logic documentation a schema has — better than any comment, because it's necessarily accurate (it's the actual logic, not someone's stale description of it) — and several backends here already fetch it (Oracle's `TEXT_VC`, flagged in the audit as truncation-prone for long bodies). Where a backend's cheap catalog-view path truncates long definitions (Oracle's is the known case, likely to recur elsewhere), the fix is switching to whatever LOB-safe or DDL-reconstruction facility that platform offers (Oracle's `DBMS_METADATA.GET_DDL` is built exactly for this) rather than accepting a silently truncated body as good enough.

Stored procedures, functions, and UDFs are the largest structural gap the audit already named and it's worth restating why it matters beyond "completeness": Oracle's `execute()` already has real PL/SQL-block execution support (the audit calls this out directly), and every other backend here can at minimum run a function call inline — but none of them tell Gemini such objects exist at all. A question phrased around a named business concept ("show me churned customers this quarter") is often a near-verbatim match for an existing function or view someone already wrote, and reusing it is both more likely to be correct and more consistent with however the business actually defines that term than the model re-deriving its own definition of "churned" inline. This generalizes the audit's Oracle-specific finding to every backend with a queryable routine catalog (Postgres `information_schema.routines`, MySQL `information_schema.ROUTINES`, MSSQL `sys.procedures`/`sys.objects`, Snowflake and Databricks each have an `information_schema` procedures/functions view, BigQuery has routines too) — signature and a short body preview at minimum; a full body where it's not excessive.

## Comments, and what to do when there aren't any

Table and column comments are the most direct source of exactly the semantic information no structural query can ever recover — what a cryptically-named column actually means, what unit a number is in, why a table exists at all — and today literally none of the ten backends fetch them, despite every SQL-capable one here having a real, queryable place to get them from: Postgres's `pg_description`/`obj_description()`/`col_description()`, MySQL's `information_schema.COLUMNS.COLUMN_COMMENT` and `TABLES.TABLE_COMMENT`, MSSQL's `sys.extended_properties` (the `MS_Description` convention most tooling already uses), Oracle's `ALL_TAB_COMMENTS`/`ALL_COL_COMMENTS`, Redshift's Postgres-derived `pg_description` (Redshift's catalog is close enough to upstream Postgres that this is likely a near-identical query to the existing Postgres implementation), Snowflake's `INFORMATION_SCHEMA.TABLES.COMMENT`/`COLUMNS.COMMENT` (exposed directly, no separate join needed — one of the cheapest wins on this whole list), and BigQuery's table-level description, exposed through `INFORMATION_SCHEMA.TABLE_OPTIONS` (`option_name = 'description'`) — worth noting that `bigquery.py` today builds its whole schema block from `INFORMATION_SCHEMA` queries via `bigquery.Client`'s job-running path (`_run()`), not the client library's `get_table()`/`Table`/`SchemaField` object attributes, so the natural fit is another `INFORMATION_SCHEMA` query in the same style as the existing `TABLES`/`COLUMNS`/`TABLE_CONSTRAINTS` ones already there, rather than a separate object-attribute code path. BigQuery's column-level comments are less consistently exposed through `INFORMATION_SCHEMA.COLUMNS` across API versions and are worth confirming directly against current docs before committing to a query shape. Databricks' Unity Catalog supports `COMMENT` on both tables and columns as well, exposed through `information_schema` or `DESCRIBE TABLE EXTENDED`; the exact column names are worth confirming against current docs at implementation time rather than assumed, since Unity Catalog's `information_schema` surface has evolved since general availability.

The real-world catch is that most schemas were never annotated — comments require someone to have proactively written them, and plenty of production databases, especially older or organically-grown ones, simply don't have any. Fetching them everywhere they exist is close to free and should happen regardless, but it won't close the semantic gap on an uncommented schema, which is the common case, not the exception. For that gap, database introspection has a real ceiling: no query against any catalog can recover context that was never written down anywhere in the database. The only way past that ceiling is a different kind of solution entirely — letting a user attach free-text notes to a connection ("our `status` codes are `A`/`I`/`P` — active/inactive/pending", "`amt` is always in cents") that get merged into the schema block the same way a real comment would. This is worth flagging explicitly as a product decision rather than an introspection one, since it's the only lever available once "query the catalog harder" has been exhausted.

## What the current session can actually do, not just what exists

The audit's grants gap is worth narrowing, not just closing. A full grants dump — who besides the current connection can do what — is aimed at a human DBA auditing access, and most of it is irrelevant to generating a query: the model doesn't need to know that some other role can `INSERT` into a table it will never touch. What actually prevents a wrong query is knowing whether the connection actually in use right now can `SELECT` from a given table at all, since a confidently-generated query against a table the live session can't read fails at execution with a permissions error the model had no way to anticipate from a schema block that listed the table as if it were freely queryable. Where a backend can express this directly — Postgres's `has_table_privilege(current_user, ...)`, or filtering `information_schema.role_table_grants`/`TABLE_PRIVILEGES` to the current user/role rather than dumping every grantee — that's a more directly useful signal than the general-purpose grants audit item, and considerably cheaper to compute and to render in the schema text (one line per table at most, not a full grantee matrix).

Session-level settings matter the same way. The connection's effective timezone changes how `NOW()`/`CURRENT_TIMESTAMP` and relative-date arithmetic resolve, and a relative question like "orders from today" can drift by a day right at a midnight boundary if the model assumes a timezone the session isn't actually using. A single line — the session's effective timezone — is cheap on every backend here and removes a whole class of near-midnight date-boundary mistakes that no amount of column-level metadata would ever catch, since the ambiguity lives in session state, not schema.

## Scale signals: when a query needs a filter to be safe, not just fast

Distribution/sort keys (Redshift) and clustering keys are already understood in this codebase as performance-relevant metadata worth a dedicated section — Redshift's DISTKEY/SORTKEY substitute for indexes is called out in the audit as a deliberate, well-reasoned choice. Snowflake and Databricks have direct analogs worth the same treatment: Snowflake's clustering key (`SYSTEM$CLUSTERING_INFORMATION`, or the clustering key directly on `INFORMATION_SCHEMA.TABLES` for tables that have one explicitly defined) and Databricks/Delta's partition columns and Z-ORDER clustering both function the same way — a hint about what column a huge table is physically organized around, and therefore what a filter on that column buys you.

BigQuery is the one case here where this crosses from a performance hint into an outright correctness constraint, and it deserves to be called out on its own rather than folded into the general partitioning discussion: a BigQuery table can be configured to require a partition filter, meaning a query that omits a filter on the partitioning column doesn't just run slowly, it fails outright. Consistent with `bigquery.py`'s existing `INFORMATION_SCHEMA`-based approach, the partitioning column is identifiable via `INFORMATION_SCHEMA.COLUMNS.is_partitioning_column` and clustering columns via `clustering_ordinal_position` (both documented fields on that same view the existing column-fetching query could be extended to select), while the require-a-filter setting itself lives at the table level in `INFORMATION_SCHEMA.TABLE_OPTIONS` — a second query in the same family as the `TABLE_OPTIONS` lookup already recommended above for table descriptions, not a new query shape. This belongs in the schema text as an explicit instruction, not just descriptive color, for exactly the tables where it's set. The existing date-shard-family grouping (naming-convention-based, e.g. `events_20240101`) already gives the model a workable mental model for one style of time-partitioned data; native `PARTITION BY` tables are a structurally different mechanism the model currently has no visibility into at all on any backend, and where BigQuery's required-filter setting is on, the gap goes from "missed opportunity" to "query fails."

Row counts belong in this same bucket — not as a precise figure, since most sources here are estimates (Postgres's `pg_class.reltuples`, MySQL's `information_schema.TABLES.TABLE_ROWS` for InnoDB, Oracle's `ALL_TABLES.NUM_ROWS` populated by whenever stats were last gathered) rather than a live count, but as a rough order-of-magnitude signal for whether a query needs a `LIMIT`/sampling approach at all, and for the same "does this table even plausibly contain what's being asked about" sanity check date ranges provide. Redshift is a near-zero-cost case worth calling out specifically: `redshift.py` already queries `SVV_TABLE_INFO` for `diststyle`/`sortkey1`, and that same view also carries `tbl_rows` (an estimated row count) and `stats_off` (a staleness signal for exactly the caveat below) — extending the existing query's select list, not adding a new one. Snowflake's `INFORMATION_SCHEMA.TABLES.ROW_COUNT` is one of the cheaper sources here, maintained natively rather than requiring a fresh scan; BigQuery's closest equivalent is `INFORMATION_SCHEMA.TABLE_STORAGE` (`total_rows`), a metadata-only view rather than a live count, though its availability/latency characteristics are worth confirming against current docs before relying on it at schema-cache-refresh frequency. Any of these should be presented as approximate ("~1.2M rows, as of last stats refresh") rather than exact, since presenting a stale estimate as a precise fact is its own small credibility problem if a user asks the model to explain a count discrepancy later.

## Two boundary cases worth naming, not solving here

Row-level security and column masking policies (Postgres RLS, Snowflake row access policies and column masking policies, BigQuery column-level security) don't change what SQL should be written — a query is still correct as generated — but they do mean the result set returned might be silently filtered or masked in ways invisible from the schema alone. This doesn't belong in the "write the query" phase at all; it belongs, if anywhere, as a note attached to results ("this connection may have row/column-level security applied — the data shown may not represent the full table") so neither the model nor the user mistakes a policy-filtered result for the complete picture. Flagging its existence (a policy applies to this table) is cheap where the catalog exposes it; explaining its effect is not generally derivable from metadata and shouldn't be attempted.

Federated and external sources — Postgres foreign tables (FDW), Redshift Spectrum external schemas, Snowflake/Databricks external tables, BigQuery external tables, and for that matter this app's own Sheets backend viewed from any other connection's perspective — often have materially different performance and freshness characteristics than a native table: no statistics at all, a live scan of external files on every query, or staleness the source system controls rather than the database. Where a backend's catalog distinguishes external/foreign tables from native ones (most do, via a table-type flag already close to what several `get_schema()` implementations already select), surfacing that distinction as a one-word annotation is cheap and prevents the model from treating a join against a huge external table the same way it would a native one.

## Making this affordable: when to compute what

Every recommendation above adds characters to a text block that already has a hard `SCHEMA_MAX_CHARS` ceiling and a `SCHEMA_MAX_TABLES` count that already trims which tables get full detail at all — enriching every table's block makes each one bigger, which means fewer of them fit before the existing caps start cutting content that's there today. Applying all of this uniformly and eagerly to every table on every schema-cache refresh is very likely the wrong default, both for the character budget and, on backends like BigQuery/Snowflake/Databricks, for the direct compute cost of the sampling queries themselves.

The two-phase triage architecture already built for "all databases" mode (`connection_router.py`'s triage step selecting specific candidate connections before Phase B generates SQL against just those) is a natural fit for a matching two-tier introspection model: cheap, always-eager structural metadata (columns, types, keys, comments, view/routine existence — everything that's a simple catalog lookup) stays on the existing schema-cache refresh cycle and populates the always-present schema block, while the more expensive per-column enrichments (frequent-value sampling, live min/max, cardinality checks) are fetched lazily and just-in-time, once a specific question has already narrowed down to specific candidate tables — whether that's this app's existing multi-connection triage step, or an equivalent single-connection narrowing (e.g., a lightweight first pass that guesses likely-relevant tables from the question before paying for any sampling). This keeps the eager path cheap and keeps the expensive path scoped to the handful of tables a given question actually touches, rather than every table a schema happens to contain.

## Priority, roughly in order of value for the effort involved

Frequent/sample values for likely-categorical columns and min/max for date columns come first — this is the gap most directly responsible for confidently-wrong queries today, on every backend, and no other item here touches that specific failure mode at all. Table and column comments come second, purely on cost: several backends (Snowflake, BigQuery specifically) expose them almost for free, and even a partial hit rate (schemas that do have some comments) is pure upside with no query-generation downside. Precision/scale/timezone-awareness on column types and the auto-generated-column marker are next — small, cheap, uniformly available additions that close specific, well-understood classes of type-mismatch mistakes. The naming-convention "likely relationship, unconfirmed" pass follows — meaningfully valuable on exactly the backends whose real FK coverage is weakest, but needs care in how it's labeled so a guess never reads as confirmed fact. BigQuery's partition/clustering/required-filter metadata is worth pulling forward ahead of the general partitioning item given it's a correctness constraint rather than a performance hint, and is reachable through the same `INFORMATION_SCHEMA` querying style the backend already uses everywhere else. Everything in the two boundary-case sections — RLS/masking awareness, external-table flagging — is worth doing opportunistically wherever it's cheap, but shouldn't block or compete for effort against the items above it, since neither changes whether the generated SQL itself is correct.







# A two-phase model for schema introspection: broad/shallow, then narrow/deep

## The existing pattern, precisely — and where it stops today

"All databases" mode already has a two-phase shape: `connection_router.py`'s `triage_all_mode_question` (Phase A) sees a compact summary of every in-scope connection and decides which ones are actually relevant, and only those selected connections go on to `translate_routes.py`'s `_run_phase_b_fanout`/`generate_sql_for_connection` (Phase B) for real SQL generation. That's the pattern this proposal generalizes — but it's worth being exact about what today's version actually narrows, because it's narrower than it looks in two specific ways, and both matter for what comes next.

First, Phase A's "shallow" summary (`db.py`'s `build_router_candidate_summaries`, rendered by `_build_candidate_schema_block`) is `{"name", "dialect", "table_names"}` per connection — table names and dialect only, deliberately no column-level detail at all, by design (its own docstring says so directly). That's genuinely shallow content. But it's not cheap to produce: it's built by calling the exact same `get_database_schema()` every other code path uses — the full, TTL-cached, column/constraint/index/view/grant/trigger schema text — and then reducing that already-fully-introspected text down to table names via `extract_entry_names_from_schema_text`. So today's "Phase 1" pays Phase-2-level introspection cost for every in-scope connection, including the ones triage is about to discard, and only saves prompt tokens, not introspection work. That's fine as far as it goes — the underlying `get_schema()` calls are catalog-only queries, not live-data sampling, so the cost that's being paid redundantly is real but bounded — but it means today's version doesn't demonstrate the actual savings this proposal is after, and any new attribute that IS expensive (a live `GROUP BY`, an aggregate scan) cannot be allowed to ride along the same "fetch everything, trim after" path or the whole point of a shallow phase is lost.

Second, and more directly relevant to what you asked: today's narrowing only ever operates at the connection level. Once a connection is selected, Phase B fetches that connection's entire schema — every table in it, up to `SCHEMA_MAX_TABLES` (200) — with no further narrowing to the specific tables the question actually concerns. There is no table-level triage anywhere in this codebase today, in either mode: single-connection mode has never had any narrowing step at all (prompt goes straight to the full cached schema), and all-dbs mode's Phase A stops at "which connections," never asking "which tables within them." Extending the two-phase pattern to schema *attributes* — sample values, comments, cardinality, and everything else the prior recommendations covered — genuinely requires adding this table-level narrowing step, because most of what belongs in a deep, expensive phase only makes sense scoped to a small, specific set of tables. That's a real, new piece of architecture, not a relabeling of something that already exists, and this proposal says so explicitly rather than implying it's already half-built.

## What actually decides an attribute's phase

Two independent factors turn out to collapse into the same split for almost every attribute, which is why a clean two-way division works at all rather than needing three or four tiers.

Cost is the first and most obvious: does producing this attribute require only a catalog/metadata lookup (a join against `information_schema`-style system views, or a session-level setting), or does it require a live query against the table's actual data (a `GROUP BY`, a `MIN`/`MAX` scan, a fresh `COUNT`)? Catalog-only lookups are cheap and safe to run broadly, across every table in every in-scope connection, on the existing schema-cache refresh cycle — there's no reason to gate them behind a narrowing decision at all. Live-data lookups are exactly the ones that must not run broadly: multiplied across every column of every table in a large schema, they're both a real latency cost and, on usage-billed engines (BigQuery's bytes-scanned pricing being the sharpest case), a real recurring dollar cost for tables that were never going to be queried.

Prompt-character budget is the second factor, and it's the reason a few attributes split into "broad, but only a pointer" versus "narrow, but the full thing," even though the underlying catalog query for both halves is equally cheap. A view's full SQL body, or a stored procedure's full body, costs nothing extra to fetch from the catalog whether or not that view ends up relevant — but including every view's complete body for all 200 tables in the base schema block would blow through `SCHEMA_MAX_CHARS` for content that's dead weight on every question except the rare one that actually needs it. So the cheap-to-fetch/expensive-to-include split still lands the same way as the cost split above, just for a different reason: existence and a short signature are worth including broadly; the full body is worth including only once a table or routine is confirmed relevant.

One attribute is worth naming as the genuine exception, because it doesn't fit either factor cleanly: the naming-convention "likely relationship, unconfirmed" heuristic proposed in the prior document (a `customer_id` column matched against another table's primary key by name/type, absent a real FK constraint) needs Phase 1's breadth as its *input* — you can't tell whether a column's name plausibly matches another table's key without having already seen that other table's columns — but its *output* is only worth rendering into the prompt for the narrow set of tables actually in play, exactly like a view body. It's computed from data Phase 1 already collected, at essentially zero extra query cost, but it belongs in Phase 2's rendered output for the same character-budget reason a view body does.

## Phase 1 — broad, shallow: every table, every in-scope connection, catalog-only

This is what stays on the existing schema-cache TTL and gets computed for the full breadth of tables `SCHEMA_MAX_TABLES` already allows through, in every connection currently in scope — not just the ones a question turns out to need, because at this point no question has narrowed anything yet. Everything here is a metadata/catalog lookup; nothing here ever touches a row of real data.

Structural: table and column names, column types including precision/scale/length and timezone-awareness (already sitting one column away from what today's `information_schema.COLUMNS`-style queries select, per the prior document), nullability and default values, PK/FK/unique constraints, indexes where the engine has them, views (existence, not body), triggers, and an explicit auto-generated/identity marker per column — this is essentially today's `get_schema()` output plus the "column semantics beyond the raw type name" additions from the prior document, none of which need a live query.

Comments: table and column comments, wherever the catalog exposes them — this is squarely Phase 1 because it's cheap and because it's plausibly useful for making the narrowing decision itself, not just for the eventual generation step. A comment that says "legacy, replaced by orders_v2" is exactly the kind of signal that should influence which table gets selected in the first place, not just how it gets described once selected.

Row-count estimates from maintained catalog stats — `pg_class.reltuples`, `information_schema.TABLES.TABLE_ROWS`, `ALL_TABLES.NUM_ROWS`, Redshift's `SVV_TABLE_INFO.tbl_rows` (already queried in that same view for DISTKEY/SORTKEY, so this is a free column addition, not a new query), Snowflake's `INFORMATION_SCHEMA.TABLES.ROW_COUNT`. Same reasoning as comments: cheap, and directly useful as narrowing signal (disambiguating a populated table from an empty or near-empty one with a similar name), not merely descriptive.

Routine existence and signatures: stored procedure/function/UDF names and parameter signatures, without full bodies — cheap catalog reads, and knowing a function named `calculate_churn` exists at all is exactly the kind of thing that should be available when deciding whether a question can be answered by reusing it, which is a narrowing-relevant decision, not just a generation-time nicety.

Scale/physical-layout signals: distribution and sort keys (Redshift), clustering keys (Snowflake, Databricks), partition columns and, specifically for BigQuery, the required-partition-filter setting — all catalog-level facts with no live query involved. BigQuery's required-filter flag in particular belongs in Phase 1 without exception: it can determine whether a table is even a viable candidate for a given question (an aggregate-without-filter question against a required-filter table needs to be ruled out or handled specially before any SQL gets generated at all), so deferring it to a narrow phase would be actively harmful, not just suboptimal.

Session/connection-level facts, each contributing one line rather than one per table: effective timezone, default collation, and — reframed from the audit's general grants gap — the current session's own effective read access per table (filtered to `current_user`/current role, not a full grantee audit), all catalog or session-variable lookups with no per-row cost regardless of table count.

Governance flags: whether a row-level-security or column-masking policy applies to a table, and whether a table is external/federated rather than native — both a cheap boolean/flag read off the catalog, worth including broadly since, like the BigQuery filter requirement, a policy or an external-table's different performance profile can matter before a table is even chosen as a candidate.

Existence-only pointer for expensive content: view and routine names get a "this exists" line in Phase 1 even though their full bodies are Phase 2 — the pointer costs nothing and lets the narrowing step (or the model doing the narrowing) know a deep artifact is available to ask for.

## Phase 2 — narrow, deep: only the tables a question actually reaches

Everything here either requires a live query against actual data, or is cheap to fetch but too large to justify including broadly. It only runs for the small set of tables (and connections) that survive the narrowing step described below, and it is the layer this codebase does not have any equivalent of today, for either mode.

Live-data-dependent, the core of the prior document's biggest single recommendation: frequent/sample values for columns that look categorical, and min/max for date and numeric columns. Both require an actual `GROUP BY`/`MIN`/`MAX` against the table, which is exactly the kind of query that must never run against all 200 tables in a schema — this is the clearest, highest-value case for narrowing to exist at all.

Cardinality/distinct-value checks used to decide whether frequent-value sampling is even worth attempting for a given column (`pg_stats.n_distinct`, `APPROX_COUNT_DISTINCT`) — technically a catalog-adjacent, cheap-per-call lookup, but it only has a reason to run at all once a table is already narrowed, since its only purpose is gating the Phase-2 sampling decision above; running it broadly would just be paying for a gate nobody's about to walk through.

Fresh/live row counts, where a stale catalog estimate genuinely isn't good enough for the question at hand — this is the one Phase 1 attribute that has a live-query Phase 2 counterpart, and the two should be presented as complementary rather than duplicated: Phase 1's estimate answers "is this table plausibly relevant," Phase 2's live count (fetched only for tables already selected, and only when needed) answers a question that actually depends on precision.

Full view and stored-procedure/function bodies — cheap queries individually, but only worth their character cost for the specific artifacts a narrowed question is actually touching, per the character-budget reasoning above. Oracle's `TEXT_VC` truncation issue (flagged in both prior documents) matters most here: a body worth including in full should actually be fetched in full, via `DBMS_METADATA.GET_DDL` or the equivalent, precisely because Phase 2 is the one place a body's full text was judged worth its cost.

The naming-convention "likely relationship, unconfirmed" pass, rendered only for the narrowed table set, computed from Phase 1 data already in hand (no new query, just a comparison over metadata already fetched broadly) — the one attribute, as noted above, whose placement is about render cost rather than compute cost.

Anything genuinely deep on the governance/federation boundary cases from the prior document — e.g., actually characterizing what a row-level-security policy filters, rather than just flagging that one exists — stays low-priority and belongs here if it's ever built at all, since it would need per-row or per-policy detail no broad pass could produce cheaply.

## Making table-level narrowing exist at all

Phase 2 has nowhere to attach without a "which tables" decision, and today only "which connections" exists, and only in all-dbs mode. Two things need to be added, and they're different problems, not one problem in two modes.

For all-dbs mode, the natural extension is widening `triage_all_mode_question`'s existing JSON contract rather than inventing a parallel mechanism: it already asks the model for per-selected-connection `database_prompts` (a rewritten question per connection, keyed by index, validated leniently — `_clean_database_prompts` tolerates a missing or malformed entry for any index without failing the whole triage attempt). A sibling field — `relevant_tables: {int_index: [table_name, ...]}` — follows the identical shape and the identical tolerance: a missing or malformed entry for some connection just means Phase 2 enrichment is skipped for that connection's tables (falling back to Phase-1-only content, today's actual behavior), never a reason to fail or retry the whole triage call. This reuses a validated pattern already in production rather than adding a new one.

Single-connection mode has no triage call to extend at all — prompt goes straight to schema-plus-generation — so it needs a new, small step rather than an extension of anything existing: a lightweight table-relevance pass over that one connection's own Phase 1 table list (the same kind of cheap classification `triage_all_mode_question` already does, just scoped to one connection's tables instead of a cross-connection list, or even a non-LLM keyword/name-overlap heuristic against the prompt text if an extra model call per turn isn't worth it). This is worth flagging plainly as new work with no existing equivalent to lean on, rather than implying it's a small extension the way the all-dbs side is.

Both modes want the same escape hatch for small schemas: below some table-count threshold (a natural reuse of the existing `SCHEMA_MAX_TABLES`-style knobs, just a smaller one — a schema of, say, 15 tables has no meaningful "narrow" subset distinct from "broad" at all), skip the narrowing decision entirely and just run Phase 2 enrichment for every table. This avoids paying for a triage/relevance step whose answer would be "all of them anyway" on the common case of a small, single-purpose database.

## Caching Phase 2 without losing the point of narrowing it

`schema_cache.py` is deliberately a generic, tiny `key -> (text, expiry)` store — its own `get`/`set`/`invalidate` don't know or care what the key represents, only that it's a stable string. Phase 1 keeps using it exactly as today, keyed per connection. Phase 2 needs its own entries, not a bigger version of the same one: a composite key such as `f"{connection_cache_key}::{table_name}"`, populated lazily only as tables actually get selected by the narrowing step, reusing the exact same `get`/`set`/`invalidate` calls with no changes to that module at all. This preserves the actual point of narrowing — a table that's never selected never gets a cache entry and never pays a live-query cost, cold or warm — while still letting a repeatedly-asked-about "hot" table benefit from caching its sample values/min-max/live count the same way Phase 1 content already benefits today. A separate, shorter TTL for Phase 2 entries is worth considering independently of Phase 1's: sample-value/row-count data drifts differently than structural metadata does, and the two don't need to expire on the same schedule just because they happen to share the same cache module.
