# A two-phase model for schema introspection: broad/shallow, then narrow/deep

Scope note: "narrow" describes where Phase 2 is headed, not where it starts. For this phase of the product, table-level narrowing is deferred (see "Table-level narrowing: deferred, not part of this phase" below) — Phase 2 rolls out as an unconditional deep pass over every table of a connection the existing, unmodified connection-level triage selects. The phase-assignment reasoning below still holds either way; what changes with table-level narrowing, whenever it's eventually built, is only how much of Phase 2's output gets rendered into the prompt for a given connection, not which attributes belong in which phase.

## The existing pattern, precisely — and where it stops today

"All databases" mode already has a two-phase shape: `connection_router.py`'s `triage_all_mode_question` (Phase A) sees a compact summary of every in-scope connection and decides which ones are actually relevant, and only those selected connections go on to `translate_routes.py`'s `_run_phase_b_fanout`/`generate_sql_for_connection` (Phase B) for real SQL generation. That's the pattern this proposal generalizes — but it's worth being exact about what today's version actually narrows, because it's narrower than it looks in two specific ways, and both matter for what comes next.

First, Phase A's "shallow" summary (`db.py`'s `build_router_candidate_summaries`, rendered by `_build_candidate_schema_block`) is `{"name", "dialect", "table_names"}` per connection — table names and dialect only, no column-level detail at all today, by design (its own docstring says so directly). That's genuinely shallow content. But it's not cheap to produce: it's built by calling the exact same `get_database_schema()` every other code path uses — the full, TTL-cached, column/constraint/index/view/grant/trigger schema text — and then reducing that already-fully-introspected text down to table names via `extract_entry_names_from_schema_text`. So today's "Phase 1" pays Phase-2-level introspection cost for every in-scope connection, including the ones triage is about to discard, and only saves prompt tokens, not introspection work. That's fine as far as it goes — the underlying `get_schema()` calls are catalog-only queries, not live-data sampling, so the cost that's being paid redundantly is real but bounded — but it means today's version doesn't demonstrate the actual savings this proposal is after, and any new attribute that IS expensive (a live `GROUP BY`, an aggregate scan) cannot be allowed to ride along the same "fetch everything, trim after" path or the whole point of a shallow phase is lost.

This mechanism itself — fetch the full schema for every in-scope connection, but pass only a reduced projection of it to the triage LLM call that decides which connections to contact — is not changing under this proposal; it's the right shape and stays. The one adjustment is what that reduced projection contains. Today it's table names only, as above; going forward it should also carry column names (not types, not keys, not any other column-level detail — just the names), so the triage step can tell apart two similarly-named tables, or a table whose columns obviously don't match the question, in a way "table names alone" genuinely can't. This costs nothing new to produce: column names are already sitting in the same fully-introspected schema text `extract_entry_names_from_schema_text` already reduces down to table names, so widening that reduction to also keep column names is a small, self-contained change to `build_router_candidate_summaries`/`_build_candidate_schema_block`, not a new introspection cost or a new query.

Second: today's narrowing only ever operates at the connection level, and this proposal's original draft treated adding a further, table-level narrowing step (a new "which tables within a selected connection" decision, on top of "which connections") as a near-term, load-bearing piece of this design. On reflection, given how small an actual dataset is expected to be in this phase of the product — the large majority of connections will have on the order of a dozen or so tables, not hundreds — that table-level decision step doesn't earn its cost yet. Its only job is to stop expensive, live-data attributes from running against tables a question doesn't need; at a dozen tables, running those same attributes against all of them costs about the same as running them against a hand-picked subset, so the decision step would be pure added latency (an extra LLM call, or new heuristic logic) and pure added risk (a wrong exclusion) with nothing to show for it. So table-level narrowing is deferred rather than built now — treated as a scaling mechanism to add later if actual customer schemas grow large enough to need it, not as part of this design's near-term shape. Section "Table-level narrowing: deferred, not part of this phase" below covers what that means concretely for Phase 2's rollout, and Section "Summary table" reflects it directly.

## What actually decides an attribute's phase

Two independent factors turn out to collapse into the same split for almost every attribute, which is why a clean two-way division works at all rather than needing three or four tiers.

Cost is the first and most obvious: does producing this attribute require only a catalog/metadata lookup (a join against `information_schema`-style system views, or a session-level setting), or does it require a live query against the table's actual data (a `GROUP BY`, a `MIN`/`MAX` scan, a fresh `COUNT`)? Catalog-only lookups are cheap and safe to run broadly, across every table in every in-scope connection, on the existing schema-cache refresh cycle — there's no reason to gate them behind a narrowing decision at all. Live-data lookups are exactly the ones that must not run broadly: multiplied across every column of every table in a large schema, they're both a real latency cost and, on usage-billed engines (BigQuery's bytes-scanned pricing being the sharpest case), a real recurring dollar cost for tables that were never going to be queried.

Prompt-character budget is the second factor, and it's the reason a few attributes split into "broad, but only a pointer" versus "narrow, but the full thing," even though the underlying catalog query for both halves is equally cheap. A view's full SQL body, or a stored procedure's full body, costs nothing extra to fetch from the catalog whether or not that view ends up relevant — but including every view's complete body for all 200 tables in the base schema block would blow through `SCHEMA_MAX_CHARS` for content that's dead weight on every question except the rare one that actually needs it. So the cheap-to-fetch/expensive-to-include split still lands the same way as the cost split above, just for a different reason: existence and a short signature are worth including broadly; the full body is worth including only once a table or routine is confirmed relevant.

One attribute is worth naming as the genuine exception, because it doesn't fit either factor cleanly: the naming-convention "likely relationship, unconfirmed" heuristic proposed in the prior document (a `customer_id` column matched against another table's primary key by name/type, absent a real FK constraint) needs Phase 1's breadth as its *input* — you can't tell whether a column's name plausibly matches another table's key without having already seen that other table's columns — but its *output* is only worth rendering into the prompt for the tables actually in play (today, a selected connection's tables; later, a narrowed subset of them), exactly like a view body. It's computed from data Phase 1 already collected, at essentially zero extra query cost, but it belongs in Phase 2's rendered output for the same character-budget reason a view body does.

## Phase 1 — broad, shallow: every table, every in-scope connection, catalog-only

This is what stays on the existing schema-cache TTL and gets computed for the full breadth of tables `SCHEMA_MAX_TABLES` already allows through, in every connection currently in scope — not just the ones a question turns out to need, because at this point no question has narrowed anything yet. Everything here is a metadata/catalog lookup; nothing here ever touches a row of real data.

Structural: table and column names, column types including precision/scale/length and timezone-awareness (already sitting one column away from what today's `information_schema.COLUMNS`-style queries select, per the prior document), nullability and default values, PK/FK/unique constraints, indexes where the engine has them, views (existence, not body), triggers, and an explicit auto-generated/identity marker per column — this is essentially today's `get_schema()` output plus the "column semantics beyond the raw type name" additions from the prior document, none of which need a live query.

Comments: table and column comments, wherever the catalog exposes them — squarely Phase 1 because it's cheap, and part of the same full per-connection schema Phase B/single-connection generation already consumes today. It's also worth naming as a candidate for the triage summary itself, alongside table and column names, should that ever prove useful in practice — a comment that says "legacy, replaced by orders_v2" is exactly the kind of signal that could influence which *connection* gets selected in all-dbs mode, not just how a table gets described once a connection is chosen — but that's a separate, later decision from the table-names-plus-column-names scope already settled on above, not something this proposal is deciding now.

Row-count estimates from maintained catalog stats — `pg_class.reltuples`, `information_schema.TABLES.TABLE_ROWS`, `ALL_TABLES.NUM_ROWS`, Redshift's `SVV_TABLE_INFO.tbl_rows` (already queried in that same view for DISTKEY/SORTKEY, so this is a free column addition, not a new query), Snowflake's `INFORMATION_SCHEMA.TABLES.ROW_COUNT`. Same reasoning as comments: cheap, part of the full per-connection schema regardless, and — like comments — a plausible future candidate for the triage summary if disambiguating a populated table from an empty one with a similar name ever turns out to matter, though that's not part of what's being decided here.

Routine existence and signatures: stored procedure/function/UDF names and parameter signatures, without full bodies — cheap catalog reads, useful once a connection is selected for deciding whether a question can be answered by reusing an existing function rather than reinventing its logic inline.

Scale/physical-layout signals: distribution and sort keys (Redshift), clustering keys (Snowflake, Databricks), partition columns and, specifically for BigQuery, the required-partition-filter setting — all catalog-level facts with no live query involved. BigQuery's required-filter flag in particular belongs in Phase 1 without exception: it can determine whether a table is even a viable candidate for a given question (an aggregate-without-filter question against a required-filter table needs to be ruled out or handled specially before any SQL gets generated at all), so deferring it to a narrow phase would be actively harmful, not just suboptimal.

Session/connection-level facts, each contributing one line rather than one per table: effective timezone, default collation, and — reframed from the audit's general grants gap — the current session's own effective read access per table (filtered to `current_user`/current role, not a full grantee audit), all catalog or session-variable lookups with no per-row cost regardless of table count.

Governance flags: whether a row-level-security or column-masking policy applies to a table, and whether a table is external/federated rather than native — both a cheap boolean/flag read off the catalog, worth including broadly since, like the BigQuery filter requirement, a policy or an external-table's different performance profile can matter before a table is even chosen as a candidate.

Existence-only pointer for expensive content: view and routine names get a "this exists" line in Phase 1 even though their full bodies are Phase 2 — the pointer costs nothing and lets whatever consumes it (today, Phase 2 itself once a connection is selected; later, a table-level narrowing step, if one is ever built) know a deep artifact is available to ask for.

## Phase 2 — deep: for this phase of the product, applied to every table of a selected connection

Everything here either requires a live query against actual data, or is cheap to fetch but too large to justify including broadly. The "narrow" half of this phase's name describes where this is headed, not where it starts: since table-level narrowing is deferred (see below), Phase 2 for now runs unconditionally over every table of whichever connection(s) survive the existing connection-level triage — no further "which tables" decision, because at the dataset sizes this product phase actually sees, unconditional and narrowed cost about the same anyway. It is still scoped by connection, the one selection mechanism that already exists: a connection triage never selects is never touched by Phase 2 at all, and never pays a live-query cost for it. This is the layer this codebase does not have any equivalent of today, for either mode.

Live-data-dependent, the core of the prior document's biggest single recommendation: frequent/sample values for columns that look categorical, and min/max for date and numeric columns. Both require an actual `GROUP BY`/`MIN`/`MAX` against the table — exactly the kind of query that must never run against all 200 tables of every in-scope connection regardless of whether it was ever selected, which is what the connection-level triage step already prevents today, and would be the clearest, highest-value case for table-level narrowing too, if and when a connection's own table count ever grows large enough to need it.

Cardinality/distinct-value checks used to decide whether frequent-value sampling is even worth attempting for a given column (`pg_stats.n_distinct`, `APPROX_COUNT_DISTINCT`) — a catalog-adjacent, cheap-per-call lookup. This gate is worth keeping regardless of whether table-level narrowing ever gets built: it's a per-*column* decision, not a per-table one, and a free-text `description` column or a UUID primary key is exactly as wasteful to run frequent-value sampling against whether it's one of a dozen tables or one of two hundred. Table-count narrowing and column-cardinality gating solve different problems — how many tables get Phase 2 at all, versus which columns within an in-scope table are worth sampling — and deferring the former (per the section below) doesn't touch the case for keeping the latter.

Fresh/live row counts, where a stale catalog estimate genuinely isn't good enough for the question at hand — this is the one Phase 1 attribute that has a live-query Phase 2 counterpart, and the two should be presented as complementary rather than duplicated: Phase 1's estimate answers "is this table plausibly relevant," Phase 2's live count (fetched only for a selected connection's tables, and only when needed) answers a question that actually depends on precision.

Full view and stored-procedure/function bodies — cheap queries individually, but only worth their character cost for the tables a question is actually touching, per the character-budget reasoning above. For now that means every table of a selected connection (no table-level narrowing yet), which is still a real saving over including every body for every in-scope connection regardless of whether it was selected at all. Oracle's `TEXT_VC` truncation issue (flagged in both prior documents) matters most here: a body worth including in full should actually be fetched in full, via `DBMS_METADATA.GET_DDL` or the equivalent, precisely because Phase 2 is the one place a body's full text was judged worth its cost.

The naming-convention "likely relationship, unconfirmed" pass, rendered for a selected connection's tables, computed from Phase 1 data already in hand (no new query, just a comparison over metadata already fetched broadly) — the one attribute, as noted above, whose placement is about render cost rather than compute cost.

Anything genuinely deep on the governance/federation boundary cases from the prior document — e.g., actually characterizing what a row-level-security policy filters, rather than just flagging that one exists — stays low-priority and belongs here if it's ever built at all, since it would need per-row or per-policy detail no broad pass could produce cheaply.

## Table-level narrowing: deferred, not part of this phase

The original shape of this proposal treated a "which tables" decision — on top of all-dbs mode's existing "which connections" decision — as necessary infrastructure to build alongside Phase 2 itself: Phase 2 has nowhere to attach without it, so it seemed to come first. That's being walked back here, specifically because of how small an actual dataset is expected to be in this phase of the product. If the large majority of connections have on the order of a dozen or so tables, a "which tables within this connection" decision has no real question to answer most of the time — the answer is "all of them" — and building it now would mean carrying a whole new decision mechanism (with its own failure modes: a wrong exclusion silently drops a table a question needed) for a saving that, at this scale, barely exists. So table-level narrowing is deferred: not designed away, just not built for the current phase, and picked back up only if actual customer schemas grow large enough that unconditional Phase 2 costs something worth avoiding.

What that means concretely: Phase 2 rolls out now as an unconditional pass over every table of a connection the existing (connection-level, unmodified) triage step selects — no new decision, no new JSON field, no new single-connection pre-pass. Connection-level selection stays exactly what it is today in both what it decides (which connections) and, per the section above, close to what it passes to the triage LLM call (table names, soon joined by column names) — the only thing this proposal changes about that step at all.

When table-level narrowing is eventually worth building — as a defense mechanism against a customer whose connection genuinely does have hundreds of tables, not as a default everyone pays for — the shape sketched in the original draft of this proposal is still the right one to reach for, and is worth keeping on record rather than re-deriving from scratch at that point: for all-dbs mode, widen `triage_all_mode_question`'s existing JSON contract with a sibling field next to today's per-connection `database_prompts` — something like `relevant_tables: {int_index: [table_name, ...]}` — reusing the same lenient-validation pattern `_clean_database_prompts` already establishes (a missing or malformed entry for one connection just means Phase 2 runs unnarrowed for that connection's tables, never a reason to fail or retry the whole triage call). Single-connection mode has no triage call to extend at all, so it would need new work rather than an extension of anything existing: a lightweight table-relevance pass over that one connection's own Phase 1 table list, or a non-LLM keyword/name-overlap heuristic against the prompt text if an extra model call per turn isn't worth its cost even at that point. And whenever it is built, it should still carry the same size-based escape hatch this section is effectively generalizing to the whole product for now: below some table-count threshold, skip the narrowing decision and just run Phase 2 unconditionally, because a schema that small has no meaningful "narrow" subset distinct from "broad" regardless of how large the product's other customers have grown.

## Caching Phase 2

`schema_cache.py` is deliberately a generic, tiny `key -> (text, expiry)` store — its own `get`/`set`/`invalidate` don't know or care what the key represents, only that it's a stable string. Phase 1 keeps using it exactly as today, keyed per connection. Phase 2 needs its own entries, not a bigger version of the same one: a composite key such as `f"{connection_cache_key}::{table_name}"`, reusing the exact same `get`/`set`/`invalidate` calls with no changes to that module at all. Without table-level narrowing, this gets populated for every table of a connection once that connection is selected — not lazily for a hand-picked few, since there's no further "which tables" decision to be lazy about yet — but the connection-level gate still matters just as much: a connection triage never selects never gets a Phase 2 cache entry and never pays a live-query cost for it, cold or warm. If table-level narrowing is ever built (see above), this same per-`(connection, table)` keying is already the right shape to make it lazy at that point too, with no cache-layer change needed — only the code deciding which tables to populate would change. A separate, shorter TTL for Phase 2 entries is worth considering independently of Phase 1's regardless: sample-value/row-count data drifts differently than structural metadata does, and the two don't need to expire on the same schedule just because they happen to share the same cache module.

## Summary table

| Attribute | Phase | Why |
|---|---|---|
| Table/column names, types, precision/scale/length, timezone-awareness | 1 | Catalog-only; needed just to describe a table at all |
| PK/FK/unique constraints, indexes, triggers | 1 | Catalog-only; today's existing `get_schema()` content |
| Auto-generated/identity column marker | 1 | Catalog-only, cheap per column |
| Table/column comments | 1 | Catalog-only; a possible future addition to the triage summary, not decided here |
| Row-count estimates (catalog stats) | 1 | Catalog-only; a possible future addition to the triage summary, not decided here |
| View/routine existence + signature | 1 | Cheap; full body deferred (see Phase 2) |
| Distribution/sort/clustering/partition keys | 1 | Catalog-only |
| BigQuery required-partition-filter flag | 1 | Correctness-gating; must be known before a table is even a candidate |
| Session timezone, default collation | 1 | One fact per connection, session-level lookup |
| Current-user effective table access | 1 | Catalog/session lookup, narrowed to current user already |
| RLS/masking policy flag, external/federated flag | 1 | Cheap boolean; can affect candidacy itself |
| Frequent/sample values for categorical columns | 2 | Requires a live `GROUP BY` |
| Min/max for date/numeric columns | 2 | Requires a live scan |
| Cardinality/distinct-value checks | 2 | Only meaningful as a gate once a table is already selected |
| Fresh/live row counts | 2 | Live query; Phase 1's estimate already covers the broad case |
| Full view/routine bodies | 2 | Cheap query, but a character-budget cost only worth paying for a selected connection's tables |
| Naming-convention "likely relationship" pass | 2 | Computed from Phase 1 data; rendered only for a selected connection's tables (character budget, not query cost) |
| Detailed RLS/masking policy effects, external-source freshness detail | 2 (low priority) | Needs per-policy/per-row depth no broad pass could produce cheaply |
| Connection-triage summary content (table names + column names) | n/a — a projection of Phase 1, not its own attribute | Stays the existing connection-selection mechanism; widened from table-names-only to also include column names |
| Table-level narrowing ("which tables within a selected connection") | Deferred | Not built for this product phase — most schemas are small enough that unconditional Phase 2 costs the same as narrowed; revisit as a defense mechanism if/when customer schemas grow large |
